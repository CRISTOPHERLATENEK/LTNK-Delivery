Alguns campos de retorno são preenchidos pela adquirente durante ou após o processamento da transação:

| Campo               | Descrição                                         |
| ------------------- | ------------------------------------------------- |
| `acquirer`          | Nome da adquirente.                               |

# Anonimização (/docs/anonimizacao)



Anonimização remove ou mascara dados pessoais associados a pagamentos, reduzindo o risco de identificação direta ou indireta.

## Conceito [#conceito]

Depois de anonimizado, o dado deixa de ser dado pessoal, e a pessoa não pode mais ser reidentificada por aquele payload.

Exemplo antes da anonimização:

```json
{
  "CPF": "123.456.789-00",
  "Nome": "Fulano"
}
```

Exemplo depois da anonimização:

```json
{
  "Nome": "*************",
  "CPF": "***********"
}
```

> O mecanismo substitui todo o conteúdo de extras dos pagamentos anonimizados por valores mascarados, mesmo quando existirem outras chaves no objeto.

## Anonimizar pagamentos [#anonimizar-pagamentos]

```http
POST /smarttef/manager/erp/store/payments/anonymize
```

```json
{
  "payments_identifers": [
    "01970d18-aac3-7ff4-ba76-78e785409d09"
  ]
}
```

| Campo                 | Obrigatório | Descrição                                                         |
| --------------------- | ----------- | ----------------------------------------------------------------- |
| `payments_identifers` | Sim         | Lista de identificadores de pagamento que devem ser anonimizados. |

## Retorno da anonimização [#retorno-da-anonimização]

```json
{
  "rowsAffected": 3,
  "hasChanges": true,
  "message": "Payments anonymized successfully"
}
```

| Campo          | Tipo      | Descrição                                          |
| -------------- | --------- | -------------------------------------------------- |
| `rowsAffected` | `number`  | Quantidade de pagamentos anonimizados com sucesso. |
| `hasChanges`   | `boolean` | Indica se houve alteração nos dados.               |
| `message`      | `string`  | Mensagem descritiva do resultado.                  |

Depois da anonimização, os dados pessoais deixam de ser apresentados nos retornos da API.


# Gestão (/docs/gestao)



As operações de gestão mantêm a loja pronta para executar cards no Smart TEF. Elas usam o escopo da loja e devem ser chamadas com token compatível.

## Loja [#loja]

Use as operações de loja para consultar cadastro, atualizar dados, alterar configurações e anonimizar pagamentos quando aplicável.

Endpoints detalhados: [Loja](/docs/api/loja).

## Usuários [#usuários]

Usuários representam operadores e administradores vinculados à loja. Eles podem ser listados, criados, atualizados, bloqueados e configurados para MFA.

Endpoints detalhados: [Usuários](/docs/api/usuarios).

## Terminais [#terminais]

Terminais são os POS vinculados à loja. Antes de direcionar uma ordem, confirme que o terminal está ativo, pertence à loja e não está bloqueado.

Endpoints detalhados: [Terminais](/docs/api/terminais).

## Boas práticas [#boas-práticas]

* Mantenha cadastros e terminais atualizados antes de iniciar a operação.
* Use identificadores de usuário ou serial do POS apenas quando o fluxo exigir card direcionado.
* Revise bloqueios de usuário e terminal ao investigar ordens não exibidas no POS.


# Integrador (/docs/integrador)



O escopo de integrador é usado por parceiros autorizados que administram lojas vinculadas ao Smart TEF.

Use esse escopo para ativar, desativar, bloquear, desbloquear ou reativar lojas, além de gerar e revogar tokens operacionais de loja.

## Quando usar [#quando-usar]

| Necessidade        | Operação esperada                              |
| ------------------ | ---------------------------------------------- |
| Habilitar loja     | Ativar ou reativar loja vinculada.             |
| Suspender operação | Bloquear ou desativar loja.                    |
| Liberar operação   | Desbloquear loja.                              |
| Trocar credenciais | Gerar ou revogar token da loja.                |
| Ajustar parâmetros | Listar ou alterar configurações do integrador. |

## Regras de escopo [#regras-de-escopo]

* O token de integrador deve ser usado somente nas rotas próprias de integrador.
* A loja precisa estar vinculada ao integrador autenticado.
* O token de loja gerado pelo integrador deve ser usado nas operações operacionais da loja.
* Revogue tokens em caso de troca de credenciais, suspeita de vazamento ou encerramento da integração.

Endpoints detalhados: [Integrador](/docs/api/integrador).


# Fluxo de implantação (/docs/fluxo-implantacao)



Use este fluxo como roteiro para preparar uma loja antes de operar pagamentos, impressões ou formulários em produção.

## Passo 1: preparar a loja [#passo-1-preparar-a-loja]

Confirme que a loja foi criada e habilitada no Smart TEF. Parceiros White Label devem solicitar a liberação ao atendimento comercial antes de iniciar.

## Passo 2: obter credenciais [#passo-2-obter-credenciais]

Separe o Bearer Token da loja, o Gateway Token quando aplicável e as credenciais de portal para pelo menos um usuário administrador e um operador.

Veja os detalhes em [Autenticação](./autenticacao).

## Passo 3: ativar terminais [#passo-3-ativar-terminais]

Garanta que os terminais estejam vinculados à loja, ativos e não bloqueados. Operações direcionadas para POS dependem de terminal válido.

## Passo 4: configurar gestão operacional [#passo-4-configurar-gestão-operacional]

Cadastre ou revise usuários, terminais e dados da loja. A visão geral está em [Gestão](./gestao), e os endpoints detalhados ficam em [API](/docs/api).

## Passo 5: configurar webhook [#passo-5-configurar-webhook]

Quando desejar callbacks automáticos, configure uma URL pública HTTPS para receber eventos de status.

Veja os payloads e regras em [Webhook](./webhook).

## Passo 6: validar o primeiro fluxo [#passo-6-validar-o-primeiro-fluxo]

Crie uma ordem, guarde o identificador retornado e acompanhe o status por polling ou webhook até o estado final.

Para uma validação mínima, siga o [Quickstart](./quickstart).

## Operações no POS [#operações-no-pos]

| Operação     | Cor      |
| ------------ | -------- |
| Pagamento    | Cinza    |
| Cancelamento | Vermelho |
| Impressão    | Amarelo  |

## Tipos de exibição [#tipos-de-exibição]

| Tipo        | Descrição                                                     |
| ----------- | ------------------------------------------------------------- |
| `NRM`       | Ordem normal, disponível na lista de operações.               |
| `CRD_UNICO` | Ordem direcionada a um único destino, exibida com prioridade. |

Quando `order_type` for `CRD_UNICO`, informe apenas um destino: `user_id` ou `serial_pos`. Os dois campos não devem ser enviados juntos.

## Regras gerais de criação [#regras-gerais-de-criação]

| Regra                 | Aplicação                                                                                                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CNPJ                  | Quando informado no payload, deve pertencer ao mesmo escopo do token usado na requisição.                                                                                               |
| Destino único         | `serial_pos` e `user_id` são mutuamente exclusivos.                                                                                                                                     |
| Duplicidade funcional | Identificadores externos como `charge_id`, `print_id` e `form_name` não devem ser reutilizados enquanto houver operação pendente, processando ou em fluxo de estorno para a mesma loja. |
| Cancelamento          | Cancelamentos pelo ERP se aplicam a ordens ainda pendentes.                                                                                                                             |
| Consulta por período  | Em listagens por período, use janelas curtas e evite reprocessar grandes intervalos quando o webhook estiver configurado.                                                               |

## Juros de parcelamento [#juros-de-parcelamento]

| Valor      | Descrição                                     |
| ---------- | --------------------------------------------- |
| `F_STORE`  | Padrão. A loja paga os juros do parcelamento. |
| `F_CLIENT` | O cliente paga os juros do parcelamento.      |

## Campos extras [#campos-extras]

O campo `extras` carrega informações adicionais da ordem, como `CPF`, `CNPJ`, `Nome` ou dados de pedido. Use `has_details` para definir se esses dados aparecem em uma tela auxiliar.

## Convenções de retorno [#convenções-de-retorno]

* Campos de adquirente como `autorization_code`, `nsu_host`, `acquirer`, `coupon` e `payment_value` podem retornar `null` até o fim do processamento.
* Quando `order_type` for `CRD_UNICO`, envie somente um destino: `user_id` ou `serial_pos`.
* No payload de pagamento, `type` será `PAYMENT`. No payload de impressão, `type` será `PRINT`.
* Em anonimização, todo o conteúdo de `extras` pode ser substituído por valores mascarados.

## Envelope de resposta [#envelope-de-resposta]

As APIs retornam o status HTTP e um objeto `data`. Em erros de validação ou regra de negócio, `data.message` pode conter uma lista de mensagens.

```json
{
  "status": 400,
  "data": {
    "message": ["Loja não encontrada"],
    "timestamp": "2026-02-09T12:00:00.000Z",
    "path": "/smarttef/commands/erp/order/create"
  }
}
```

| HTTP  | Uso comum                                                  |
| ----- | ---------------------------------------------------------- |
| `400` | Campo inválido ou operação bloqueada por regra de negócio. |
| `401` | Token ausente, inválido, bloqueado ou incompatível.        |
| `404` | Entidade não encontrada.                                   |
| `409` | Conflito de estado ou duplicidade funcional.               |


# Autenticação (/docs/autenticacao)



Os endpoints da API Smart TEF usam JSON e autenticação por Bearer Token. Em rotas protegidas, também pode ser necessário enviar o Gateway Token no header de assinatura.

## Headers comuns [#headers-comuns]

| Nome                        | Descrição                                                  | Valor                |
| --------------------------- | ---------------------------------------------------------- | -------------------- |
| `Authorization`             | Bearer Token recebido na criação da loja ou do integrador. | `Bearer <token>`     |
| `ocp-apim-subscription-key` | Gateway Token recebido na criação da loja.                 | `<subscription-key>` |
| `Content-Type`              | Tipo de conteúdo da requisição.                            | `application/json`   |

## Token da loja [#token-da-loja]

Use o token da loja para operações do dia a dia, como criar pagamentos, consultar status, configurar webhook, gerenciar usuários e terminais da própria loja.

Quando a loja for gerenciada por um integrador, o token pode ser gerado pela rota:

```http
POST /smarttef/manager/integrator/store/get/token
```

## Token do integrador [#token-do-integrador]

Use o token do integrador apenas para operações de gestão sobre lojas integradas, como ativação, bloqueio, desbloqueio, reativação e revogação de token.

## Escopo e autorização [#escopo-e-autorização]

| Contexto   | Regra                                                                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Loja       | A operação fica limitada à loja representada pelo token. Quando um payload aceitar `cnpj`, ele deve ser o mesmo CNPJ associado ao token.           |
| Integrador | O integrador precisa estar ativo e autorizado a operar sobre a loja informada. Operações de integrador não substituem o token operacional da loja. |
| Terminal   | Operações executadas no POS dependem de terminal ativo, pertencente à loja e não bloqueado.                                                        |
| Operador   | Quando a operação receber `user_id`, o usuário deve pertencer à loja e estar apto a operar no Smart TEF.                                           |

## Direcionamento de ordens [#direcionamento-de-ordens]

Ordens podem ser abertas para a lista geral ou direcionadas para um destino específico:

* `order_type: "NRM"` deixa o card disponível na lista de operações.
* `order_type: "CRD_UNICO"` direciona o card para um único destino e exige apenas `user_id` ou apenas `serial_pos`.
* `user_id` e `serial_pos` não devem ser enviados juntos na mesma ordem.

## Credenciais de portal [#credenciais-de-portal]

Tenha disponível pelo menos:

* Um usuário administrador para configurações.
* Um usuário operador para fluxos operacionais.
* Loja criada e habilitada no ambiente correto.
* Terminal ativado, quando o fluxo depender de card direcionado a POS.

## Observações [#observações]

* Parceiros White Label devem solicitar habilitação comercial antes de começar.
* Nem todos os endpoints exigem as mesmas credenciais, mas o `Authorization` deve ser tratado como obrigatório na integração.
* Use HTTPS para webhook e para qualquer endpoint exposto publicamente pelo ERP.

## Boas práticas de segurança [#boas-práticas-de-segurança]

* Guarde tokens em variáveis de ambiente ou cofre de segredos.
* Não exponha tokens em aplicações frontend.
* Revogue e gere um novo token quando houver suspeita de vazamento.
* Registre somente identificadores técnicos nos logs e evite armazenar payloads completos com dados pessoais.


# Conceitos (/docs/conceitos)



O Smart TEF transforma uma Smart POS em um terminal de pagamento integrado ao ERP, PDV ou sistema de retaguarda, sem cabos ou equipamentos adicionais.

O sistema externo envia ordens pela API. O POS exibe cada ordem como um card operacional, processa a ação e devolve o resultado por consulta ativa ou webhook.

## Escopos de integração [#escopos-de-integração]

| Escopo     | Quando usar                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- |
| ERP Loja   | Operações do dia a dia da loja: pagamentos, impressões, formulários, usuários, terminais, webhook e configurações da loja. |
| Integrador | Administração de lojas vinculadas: ativação, bloqueio, desbloqueio, geração de token e revogação de token.                 |

Use sempre o token compatível com o escopo da operação. Token de loja não substitui token de integrador, e token de integrador não substitui o token operacional da loja.

## Tipos de card [#tipos-de-card]

| Card              | Objetivo                                                                                |

## Ciclo de uma ordem [#ciclo-de-uma-ordem]

1. O sistema externo cria a ordem pela API.
2. O Smart TEF registra o card e controla o status.
3. O POS exibe a ordem para o operador.
4. O operador executa pagamento, impressão ou preenchimento.
5. O sistema externo recebe o resultado por polling ou webhook.


# Smart TEF (/docs)



O Smart TEF permite que ERPs, PDVs, sistemas de retaguarda e plataformas externas criem ordens de pagamento, impressão e coleta de dados por API. A aplicação cliente acompanha o processamento por consulta ativa ou por webhook.

Conectado via API ou pela criação manual de cards, o Smart TEF transforma a Smart POS em um terminal integrado ao seu sistema, sem cabos ou equipamentos adicionais.

## Escopos de integração [#escopos-de-integração]

A documentação está organizada por público de consumo:

| Escopo     | Quando usar                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ERP Loja   | Integrações da própria loja: pagamentos, impressões, formulários, consultas, usuários, terminais, webhook e configuração da loja.                       |
| Integrador | Integrações que administram lojas vinculadas: ativação, bloqueio, geração ou revogação de token e reprocessamento de webhook no contexto do integrador. |

Use o token compatível com o escopo da operação. Um token de loja não substitui um token de integrador, e um token de integrador não deve ser usado para operações operacionais da loja fora das rotas previstas.

## Objetivo [#objetivo]

Servir como guia de referência para integração via API do Smart TEF com sistemas ERP, retaguarda e operações externas.

## Público-alvo [#público-alvo]

Parceiros e clientes que precisam integrar sistemas externos ao Smart TEF.

## Pré-requisitos [#pré-requisitos]

* Loja criada e habilitada no Smart TEF.
* Bearer Token para acesso à API.
* Gateway Token para chamadas protegidas.
* Credenciais do portal com usuário administrador e operador.
* URL pública para webhook, quando desejar receber atualizações automáticas.
* Terminal ativado no ambiente, quando a operação exigir envio para POS.

Parceiros White Label devem solicitar esses pré-requisitos ao atendimento comercial antes do início da integração.

1. Configure loja, usuários, terminais e webhook quando necessário.

4. Consulte o status por polling ou receba atualizações via webhook.
5. Cancele ordens pendentes, solicite estorno de pagamentos concluídos ou anonimize dados pessoais quando aplicável.

## Respostas e erros [#respostas-e-erros]

As respostas de sucesso e erro seguem um envelope JSON com `status` e `data`. Em erros de validação ou regra de negócio, `data.message` pode retornar uma lista de mensagens ou objetos com o campo inválido.

| HTTP          | Significado                                                                       |
| ------------- | --------------------------------------------------------------------------------- |
| `200` / `201` | Requisição aceita e processada.                                                   |
| `400`         | Erro de validação ou regra de negócio.                                            |
| `401`         | Token ausente, inválido, bloqueado ou incompatível com a operação.                |
| `404`         | Recurso não encontrado.                                                           |
| `409`         | Conflito, como duplicidade funcional ou operação incompatível com o estado atual. |
| `500`         | Erro inesperado no processamento.                                                 |

# Quickstart (/docs/quickstart)



Este guia mostra o caminho mínimo para criar um pagamento e acompanhar o resultado.

## 1. Configure os headers [#1-configure-os-headers]

```http
Authorization: Bearer <token-da-loja>
ocp-apim-subscription-key: <gateway-token>
Content-Type: application/json
```

Use token de loja para operações de pagamento. Token de integrador é reservado para gestão de lojas vinculadas.

## 2. Crie um pagamento [#2-crie-um-pagamento]

```http
POST /smarttef/commands/erp/order/create
```

Envie os dados da cobrança e, quando necessário, direcione a ordem para um usuário ou terminal específico. Consulte os campos em [Card de pagamento](./card-pagamento).

## 3. Guarde o identificador [#3-guarde-o-identificador]

Armazene o identificador retornado pela API, como `payment_identifier`, para consultas futuras, conciliação e suporte.

## 4. Consulte o status [#4-consulte-o-status]

```http
POST /smarttef/pooling/erp/order/get
```

Consulte a ordem até que ela chegue a um status final, como `CNC`, `CAN_ERP`, `REJ_PAG`, `EST` ou `REJ_EST`.

## 5. Configure webhook quando necessário [#5-configure-webhook-quando-necessário]

Para reduzir polling, configure o webhook da loja e receba callbacks automáticos de mudança de status.

Veja [Webhook](./webhook) para payloads, reprocessamento e boas práticas.

# Card de impressão (/docs/card-impressao)



Use ordens de impressão para enviar uma imagem ou conteúdo renderizado ao Smart TEF.

## Regras do arquivo [#regras-do-arquivo]

* Tamanho máximo recomendado de `56000` bytes.
* Largura de `450px`.
* Altura máxima de `2000px`.
* Formato `JPEG` ou `PNG`.
* Envie o conteúdo em Base64 no campo `file.data`.
* Quando `print_id` for usado, trate-o como identificador funcional da impressão na loja.

## Headers [#headers]

| Nome                        | Descrição                                  | Valor                |
| --------------------------- | ------------------------------------------ | -------------------- |
| `Authorization`             | Bearer Token recebido na criação da loja.  | `Bearer <token>`     |
| `ocp-apim-subscription-key` | Gateway Token recebido na criação da loja. | `<subscription-key>` |
| `Content-Type`              | Conteúdo da requisição.                    | `application/json`   |

## Criar impressão [#criar-impressão]

```http
POST /smarttef/commands/erp/print/create
```

Os cards de impressão servem para enviar uma imagem ao terminal.

```json
{
  "order_type": "CRD_UNICO",
  "has_details": true,
  "print_id": "12345",
  "file": {
    "name": "nome da imagem",
    "data": "iVBORw0KGgoAAAANSUhEUgAAAAEAAAABCAIAAACQd1PeAAAADElEQVQImWP4z8AAAAMBAQAY3Y20AAAAASUVORK5CYII="
  }
}
```

| Campo         | Obrigatório | Descrição                                                                                                        |
| ------------- | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `order_type`  | Não         | `CRD_UNICO` exibe imediatamente. `NRM` deixa o card em lista.                                                    |
| `user_id`     | Condicional | Usuário que receberá o card quando `order_type` for `CRD_UNICO`. Não pode ser enviado junto com `serial_pos`.    |
| `serial_pos`  | Condicional | Serial do POS que receberá o card quando `order_type` for `CRD_UNICO`. Não pode ser enviado junto com `user_id`. |
| `print_id`    | Não         | Identificador do card criado pelo ERP.                                                                           |
| `has_details` | Não         | Se `true`, exibe tela de detalhes ao clicar. Em card `CRD_UNICO` sem interação, use `false`.                     |
| `file`        | Sim         | Objeto com `name` e `data` em Base64 da imagem.                                                                  |

### Regras de impressão [#regras-de-impressão]

| Tema           | Regra                                                                                                     |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| Direcionamento | Para `CRD_UNICO`, envie apenas `user_id` ou apenas `serial_pos`.                                          |
| Arquivo        | A criação exige arquivo em Base64. Informe nome e extensão compatíveis com o formato enviado.             |
| Duplicidade    | `print_id` não deve ser reutilizado enquanto existir impressão pendente ou processando para a mesma loja. |
| Cancelamento   | Só é permitido cancelar impressões ainda pendentes.                                                       |

## Retorno da criação [#retorno-da-criação]

```json
{
  "print_identifier": "019c9618-0d2f-7405-8e07-2a3e75b20172",
  "print_status": "PDT",
  "order_type": "CRD_UNICO",
  "file": "https://storage.blob.com/smart-tef/68ab8366-29db-438e-9a39-8ca72691c0b7-SR4YK.png",
  "print_id": "189"
}
```

| Campo              | Descrição                                       |
| ------------------ | ----------------------------------------------- |
| `print_identifier` | Identificador único gerado para cada impressão. |
| `print_status`     | Status atual do card.                           |
| `order_type`       | Tipo do card, único ou normal.                  |
| `file`             | URL da imagem armazenada para download.         |
| `print_id`         | Identificador informado pelo ERP.               |

# Card de pagamento (/docs/card-pagamento)



Use ordens de pagamento para enviar uma cobrança ao Smart TEF e acompanhar seu ciclo até a conclusão, rejeição, cancelamento ou estorno.

## Headers [#headers]

| Nome                        | Descrição                                  | Valor                |
| --------------------------- | ------------------------------------------ | -------------------- |
| `Authorization`             | Bearer Token recebido na criação da loja.  | `Bearer <token>`     |
| `ocp-apim-subscription-key` | Gateway Token recebido na criação da loja. | `<subscription-key>` |
| `Content-Type`              | Conteúdo da requisição.                    | `application/json`   |

## Criar pagamento [#criar-pagamento]

```http
POST /smarttef/commands/erp/order/create
```

Esses cards podem ser enviados para um ou mais POS com a finalidade de realizar um pagamento.

Exemplo de body para um card do tipo normal:

```json
{
  "value": 1.0,
  "payment_type": "DEBIT",
  "installments": 1,
    "charge_id": "Identificador único",
  "order_type": "NRM",
  "extras": {
    "CPF": "000.000.000-00",
    "Nome": "Teste da Silva"
  },
  "has_details": false
}
```

| Campo              | Tipo      | Obrigatório | Descrição                                                                                                        |
| ------------------ | --------- | ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `value`            | `number`  | Sim         | Valor do pagamento, com separador decimal.                                                                       |
| `payment_type`     | `string`  | Não         | Tipo do pagamento. Veja [tipos de pagamento](./referencia#tipos-de-pagamento).                                   |
| `fee_type`         | `string`  | Não         | Em crédito, define quem paga os juros: `F_STORE` ou `F_CLIENT`.                                                  |
| `installments`     | `number`  | Condicional | Quantidade de parcelas. Obrigatório quando `payment_type` for `CREDIT`.                                          |
| `min_installments` | `number`  | Não         | Menor quantidade de parcelas permitida.                                                                          |
| `charge_id`        | `string`  | Não         | Identificador do card criado pelo ERP.                                                                           |
| `order_type`       | `string`  | Não         | `CRD_UNICO` para exibir imediatamente ou `NRM` para lista.                                                       |
| `user_id`          | `number`  | Condicional | Usuário que receberá o card quando `order_type` for `CRD_UNICO`. Não pode ser enviado junto com `serial_pos`.    |
| `serial_pos`       | `string`  | Condicional | Serial do POS que receberá o card quando `order_type` for `CRD_UNICO`. Não pode ser enviado junto com `user_id`. |
| `extras`           | `object`  | Não         | Campos extras como `CPF`, `CNPJ` e `Nome`.                                                                       |
| `has_details`      | `boolean` | Não         | Define se os detalhes extras podem ser exibidos em tela auxiliar.                                                |
| `form`             | `object`  | Não         | Formulário associado ao pagamento, quando aplicável.                                                             |

### Regras de pagamento [#regras-de-pagamento]

| Tema                | Regra                                                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Valor               | `value` deve ser maior ou igual a `1` e aceitar no máximo duas casas decimais.                                             |
| Parcelas            | `installments` deve ser maior que zero. Parcelamento maior que uma parcela só deve ser usado com `payment_type: "CREDIT"`. |
| Parcela mínima      | `min_installments` só se aplica a crédito e não pode ser maior que `installments`.                                         |
| Juros               | `fee_type` se aplica a crédito parcelado. Quando não enviado, considere o padrão da loja.                                  |
| Dados extras        | `extras.CPF` e `extras.CNPJ` podem ser enviados com ou sem pontuação. Use `Nome` com até 80 caracteres.                    |
| Duplicidade         | `charge_id` deve ser único para ordens pendentes, processando ou em fluxo de estorno na mesma loja.                        |
| Formulário agregado | Quando `form` for enviado na criação do pagamento, o retorno inclui os dados do formulário vinculado ao pagamento.         |

```json
{

  "payment_status": "PDT",
  "order_type": "NRM",

  "form": {

    "form_name": "form-818",
    "fill_out_type": "REQUEST_MANDATORY_FORM"
  }
}
```

| Campo                | Descrição                                   |
| -------------------- | ------------------------------------------- |
| `payment_identifier` | Identificador único gerado para cada card.  |
| `payment_status`     | Status atual do card.                       |
| `order_type`         | Tipo do card, único ou normal.              |
| `charge_id`          | Identificador informado pelo ERP.           |
| `form`               | Dados do formulário anexado, quando houver. |

# Formulários (/docs/formularios)



Formulários permitem solicitar dados estruturados durante uma operação ou como uma ordem independente.

## Criar formulário [#criar-formulário]

```http
POST /smarttef/commands/erp/form/create
```

```json
{
  "order_type": "NRM",
  "form_name": "cadastro-cliente",
  "extras": {
    "CNPJ": "12612554000131"
  },
  "form": [
    {
      "field": "Email",
      "type": "EMAIL",
      "needed": true
    }
  ]
}
```

| Campo           | Obrigatório | Descrição                                                   |
| --------------- | ----------- | ----------------------------------------------------------- |
| `order_type`    | Não         | `NRM` ou `CRD_UNICO`.                                       |
| `form_name`     | Não         | Nome de referência do formulário.                           |
| `extras`        | Não         | Dados complementares enviados pelo ERP.                     |
| `form[].field`  | Sim         | Nome do campo exibido.                                      |
| `form[].type`   | Não         | `TEXTO`, `NUMBER`, `DATA`, `CPF`, `CNPJ`, `CEP` ou `EMAIL`. |
| `form[].needed` | Não         | Define se o campo é obrigatório.                            |

## Regras de formulário [#regras-de-formulário]

| Tema                   | Regra                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Direcionamento         | Para `CRD_UNICO`, envie apenas `user_id` ou apenas `serial_pos`.                                                    |
| Campos obrigatórios    | Se algum item do formulário tiver `needed: true`, o preenchimento obrigatório deve ser considerado no fluxo do POS. |
| Formulário obrigatório | Quando a operação exigir preenchimento obrigatório, informe ao menos um campo com `needed: true`.                   |
| Duplicidade            | `form_name` não deve ser reutilizado enquanto houver formulário pendente ou processando para a mesma loja.          |
| Conclusão              | Campos obrigatórios devem retornar preenchidos como string não vazia.                                               |

## Consultar formulário [#consultar-formulário]

```http
POST /smarttef/pooling/erp/form/get
```

```json
{
  "form_identifier": "01970d18-aac3-7ff4-ba76-78e785409d09"
}
```

## Cancelar formulário pendente [#cancelar-formulário-pendente]

```http
POST /smarttef/commands/erp/form/status/cancelar
```

```json
{
  "form_identifier": "01970d18-aac3-7ff4-ba76-78e785409d09"
}
```

O cancelamento só se aplica a formulários ainda pendentes. Depois que o preenchimento estiver em processamento, acompanhe o resultado pela consulta.

## Como funciona [#como-funciona]

Quando habilitado por configuração, o Smart TEF pode operar em modo online e pesquisar cards em tempo real por meio de uma API disponibilizada pelo ERP integrado.

* O operador realiza uma pesquisa no aplicativo Smart TEF.
* O Smart TEF aciona o webhook configurado pelo parceiro.
* O ERP responde com um ou mais cards compatíveis com a busca.
* O card retornado pode ser exibido e processado no POS.

## Configuração por loja [#configuração-por-loja]

Esse webhook é configurado por loja, tanto na criação quanto na edição da loja.

```json
{
  "payment_external_hook": {
    "url": "",
    "authorization_token": ""
  },
  "name": "",
  "city": ""
}
```

| Campo                                       | Descrição                                                     |
| ------------------------------------------- | ------------------------------------------------------------- |
| `payment_external_hook.url`                 | Endpoint do ERP que receberá a pesquisa e retornará os cards. |
| `payment_external_hook.authorization_token` | Conteúdo enviado integralmente no header `Authorization`.     |
| `name`                                      | Nome da loja.                                                 |
| `city`                                      | Cidade da loja.                                               |

## Considerações técnicas [#considerações-técnicas]

* A ativação do modo online depende de configuração prévia no Smart TEF.
* O ERP precisa estar preparado para responder a consulta em tempo real.
* O contrato de resposta deve devolver cards válidos para exibição no POS.

## Exemplo de requisição para busca [#exemplo-de-requisição-para-busca]

Para essa utilização, o parceiro deve expor um método para consulta de cards.

```bash
curl --location '<URL configurada>' \
  --header 'Content-Type: application/json' \
  --data '{
    "search": "<string da pesquisa>"
  }'
```

## Exemplo de retorno da busca [#exemplo-de-retorno-da-busca]

```json
[
  {
    "value": 10,
    "payment_type": "PIX",
    "installments": 1,
    "charge_id": "019c967c-ff8e-7c83-94d1-df7eee6b5cbb",
    "order_type": "NRM",
    "extras": {
      "Nome": "teste pesquisa externa"
    },
    "serial_pos": "1231asa1112112123",
    "has_details": false
  }
]
```

O payload retornado deve seguir a mesma estrutura esperada na criação de [Card de pagamento](./card-pagamento#criar-pagamento), permitindo que o Smart TEF monte o card dinamicamente a partir da resposta do ERP.

| Evento                           | Comportamento                                                                                                         |

| Impressão processada no POS      | Envia o payload de impressão com o status atualizado.                                                                 |
| Criação ou cancelamento pelo ERP | A operação altera o status e pode ser consultada por polling. Use reprocessamento quando precisar reenviar um evento. |

## Regras de uso [#regras-de-uso]

* O integrador precisa estar ativo para operar sobre lojas vinculadas.
* A geração de token da loja deve ser tratada como operação sensível.
* Revogue o token da loja quando houver troca de credenciais, suspeita de vazamento ou encerramento da integração.
* Bloqueio, desbloqueio, desativação e reativação alteram a capacidade operacional da loja integrada.
